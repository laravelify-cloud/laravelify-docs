---
title: "Backups"
description: "Back up databases and folders to your own S3 bucket or a folder on the server, on a schedule, and restore a whole database, one table, one website, or one folder."
---

Laravelify backs up to **a bucket you own** (Amazon S3, DigitalOcean Spaces, Cloudflare R2, Backblaze B2, Wasabi, or MinIO) or to **a folder on the server**. Nothing is sent anywhere else, and the access keys are stored encrypted.

Everything lives under **Backups** in the sidebar:

| Page | What it does |
| --- | --- |
| **Databases** | Schedules for MySQL databases, the list of backups, and restores |
| **Files** | Schedules for folders (with excludes), the list of backups, and restores |
| **Backup storage** | The buckets and server folders backups go to |

<Note>
  Backups use `rclone`, which the installer adds. On a server installed before backups existed, run the update and it is installed for you.
</Note>

## 1. Add storage

Open **Backups, Backup storage, Add storage**, choose your provider, and fill in the bucket and the keys. Laravelify writes a small test file and removes it, so you know right away whether the keys work.

| Provider | Endpoint | Region |
| --- | --- | --- |
| Amazon S3 | empty | like `eu-west-1` |
| DigitalOcean Spaces | `https://nyc3.digitaloceanspaces.com` | the Space region, like `nyc3` |
| Cloudflare R2 | `https://ACCOUNT_ID.r2.cloudflarestorage.com` | `auto` |
| Backblaze B2 | `https://s3.us-west-004.backblazeb2.com` | like `us-west-004` |
| Wasabi | `https://s3.us-east-1.wasabisys.com` | your region |
| MinIO and others | your endpoint | any |

The keys need read, write, and delete access to the bucket. The first storage you add becomes the default.

### No bucket? Use a folder on the server

Choose **This server (a folder)** as the provider and give a full path, like `/backups`. Laravelify makes the folder (owned by the panel's user) and tests it like a bucket. It must be outside `/var/www` and system folders (`/etc`, `/usr`, `/tmp`, `/var/lib`, ...), so a deploy or a website can never touch it.

<Warning>
  Backups in a server folder are lost together with the server's disk. Use it to get started or next to a bucket, and copy important backups somewhere else.
</Warning>

## 2. Back up databases

**Backups, Databases, New schedule.**

- Pick **All databases** (including ones added later), or tick the databases you want. Each database is dumped on its own.
- Choose how often: every few minutes, every hour, every few hours, every day, every week, or a custom cron expression.
- Choose how many backups to **keep**. Older ones are deleted from the bucket after each run, and the newest one is always kept.

Want `app_db` every hour and everything else once a day? Make two schedules.

The empty page offers two shortcuts: **all databases every hour** and **all databases every day**.

Press **Run now** on a schedule to make a backup immediately. Each database appears in the list right away as **Waiting**, then **In progress** and **Finished**; the page updates by itself. If a backup stays on Waiting, the queue worker is not running (`sudo supervisorctl status laravelify-queue`); **Cancel waiting runs** in the schedule's menu clears it.

### Full backup

**Full backup** at the top of the page backs up everything right now: every database, or every website. It uses a schedule called *Full backup* that only runs when you start it, so its backups are listed and kept like any other.

### Bulk actions

Tick schedules to run, pause, resume, or delete several at once, and tick backups to delete several from the bucket.

### Grouped by database

**Backups and restores** shows the newest backup of each database. Press **N older backups** under it to open the rest of that database's backups underneath. File backups are grouped by schedule.

### Progress

A running backup shows what it is doing (dumping, packing, uploading) and, while it uploads to your bucket, a progress bar with the percent.

## 3. Back up folders

**Backups, Files, New schedule.** The picker works like the file manager: browse `/var/www`, tick folders and files, and press **Add to backup** or **Skip**. Each row shows whether it is **Included** or **Skipped**, so you can open a site, tick `node_modules` and `.git`, and skip them in one go.

**Every website** backs up each website in its own archive, including websites you add later, and skips what a deploy rebuilds, by site type:

| Site type | Skipped |
| --- | --- |
| Every site | `node_modules`, `.git` |
| Laravel | `vendor`, `public/build`, `bootstrap/cache`, `storage/logs`, `storage/framework/cache`, `sessions`, `views` |
| PHP | `vendor` |
| Next.js | `.next` |
| Nuxt | `.nuxt`, `.output` |
| SvelteKit | `.svelte-kit`, `build` |
| Express, NestJS, Node.js | `dist`, `.cache` |
| React, Vue.js, Svelte | `dist`, `build` |
| Angular | `dist`, `.angular` |
| Astro | `dist`, `.astro` |

Adding a website folder by hand skips the same folders for you; remove any you want to keep.

Common skips (`node_modules`, `vendor`, `.git`, `storage/logs`, ...) are one click away. A name is skipped in every folder; a path (`shop/storage/logs`) only there; `*` and `?` work. Each chosen folder (each website) is packed into its own `tar.gz`, so you can look inside, download, or restore one website without the others. **Everything** (the whole `/var/www`) stays one archive.

In the list, each run is one row, like **FULL BACKUP · 6 archives, one per website**, with every website's archive under it.

## 4. Restore

Press **Restore** at the top of the page. It walks you through three steps:

1. **Database** (or, for files, the backup set): every database with backups, with how many and the newest.
2. **Backup**: the backups of that database, newest first, with their size.
3. **What to restore**:

<Tabs>
  <Tab title="Database">
    - **Whole database**, or **some tables**: search the tables of that backup (with row counts and sizes) and tick them, or **Select all** that match.
    - Choose the database to restore into. The same name overwrites the live data. A new name restores next to it, and the database is created if it does not exist.
    - You confirm with a checkbox before anything is overwritten.
  </Tab>
  <Tab title="Files">
    - **Everything**, or browse the backup like a folder and tick the folders and files to bring back.
    - **A new restore folder** (the default) unpacks into `laravelify-restore/<date>` and overwrites nothing. **Original place** puts files back where they were, overwriting files with the same name, and asks you to confirm.
  </Tab>
</Tabs>

The restore icon on a row of the list jumps straight to step 3 for that backup.

## 5. Look inside a backup

The eye icon on a backup shows what is in it, without restoring anything:

- **Tables**, with an approximate row count and size, 25 per page, searchable. Open a table to see its `CREATE TABLE`.
- **Stored procedures**, **stored functions**, **triggers**, and **events**, each with its SQL and a copy button.
- For a file backup: the folders and files inside it, with sizes and dates.

New backups are read when they are made. An older backup is read once in the background the first time you open it.

## 6. Download

The download icon prepares a file on the server, then your browser downloads it (progress shows at the top of the page):

- **Choose parts (.sql)**: tick tables (all, or picked ones), stored procedures, functions, triggers, and events. You get one `.sql` file you can run with `mysql`; routines, triggers, and events come with `DROP ... IF EXISTS` first, so it can run twice.
- **Whole backup**: the file exactly as stored (`.sql.gz` or `.tar.gz`).

Prepared downloads are removed after a day.

## Alerts

In **Settings, Telegram bot**, **A backup or restore failed** and **A backup finished** are on by default. When a schedule finishes you get one message listing each backup with its size, and each name is a **download link** that works for 24 hours (a signed link to your bucket; the keys are never in it). If you saved your Telegram events before, tick **A backup finished** there once.

## Good to know

- Times use the timezone from **Settings, General**.
- Deleting a schedule does not delete the backups it made. Delete a backup from the list to remove its file from the bucket.
- Backups run in the queue worker, so a long backup does not slow the panel.
- A restore of a database needs the same MySQL login the panel uses, which is already set up by the installer.

<Tip>
  Test a restore before you need one. Restore a database into a new name, open it in phpMyAdmin, and check the data.
</Tip>

## Troubleshooting

<AccordionGroup>
  <Accordion title="Storage test says rclone is not installed">
    Run the update (`sudo bash /opt/laravelify/scripts/update.sh`) or install it: `sudo apt-get install -y rclone`.
  </Accordion>
  <Accordion title="The access key or secret key is wrong / Access denied">
    Check the keys and that they can write and delete in this bucket. For R2, create an API token with Object Read and Write.
  </Accordion>
  <Accordion title="The bucket does not exist">
    Create the bucket in your provider first. Laravelify does not create buckets. Also check the region.
  </Accordion>
</AccordionGroup>
